# Nastya and Potions

> [Problem on Codeforces](https://codeforces.com/problemset/problem/1851/E)

## Idea

The recipes form a graph with no cycles, so every potion can be priced after all of its ingredients have been priced. The cheapest way to get a potion is either to buy it directly, or, if it has a recipe, to pay the sum of the cheapest costs of its ingredients, and a potion we already own for free costs $0$. Because each potion has at most one recipe, there is no further choice to make, and the answer for a potion is just the smaller of buying it and mixing it.

## Approach

1. We store the best known cost of each potion in `dp`, starting from `dp=c` because buying is always possible, and we set `dp[p]=0` for the $k$ potions we already own. A free potion can never get cheaper, and anything that uses it as an ingredient should see the price $0$, so this has to be in place before any recipe is evaluated.

2. For every recipe we add an edge from each ingredient `x` to the potion `i` it helps make, and we count the ingredients in `indegree[i]`. The cost of a potion depends only on its ingredients, so a potion is ready to be priced exactly when all of them have final costs. Counting the unpriced ingredients tells us the moment that happens.

3. We process potions in topological order using a queue `q`, starting from the potions with `indegree[i]==0`, which are the ones with no recipe. Because the recipes contain no cycles, this order reaches every potion, and each potion is popped only after every ingredient has already been popped and finalised. A potion with no recipe keeps its value in `dp`, which is its purchase price, or $0$ if we own it.

4. While a potion is being finalised, every ingredient has already added its final `dp` into `sum[u]`, so `sum[u]` is the total cost of mixing it. If `hasRecipe[u]` is true we take `dp[u]=min(dp[u],sum[u])`. The flag matters because a potion with no recipe also has `sum[u]=0`, and without the flag the minimum would wrongly make it free.

5. After finalising `u`, we add `dp[u]` into `sum[v]` for every potion `v` that uses `u`, and decrement `indegree[v]`, pushing `v` once it reaches $0$. Pushing `dp[u]` only after the minimum has been taken is what makes the recipe sums use the cheapest way to get each ingredient, and handing it over exactly once per edge keeps the work linear.

## Complexity

- **Time:** $O(n + \sum m_i)$ — each potion is queued once and each recipe edge is visited once.
- **Space:** $O(n + \sum m_i)$ — the adjacency lists hold one entry per recipe edge, plus arrays of size $n$.

## Notes

- `dp` and `sum` are `long long` because a recipe can add up to about $2 \cdot 10^5$ costs of size up to $10^9$, which overflows 32-bit integers.
